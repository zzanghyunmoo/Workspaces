Cross-platform Development Environment

Windows, macOS, Linux 어디서든 같은 개발 역량을 재현하되, 하나의 만능 설치기로 모든 차이를 숨기지 않는다. 이 문서는 “저장소를 클론하고 몇 개 명령만 실행하면 전체 또는 선택 컴포넌트를 설치한다”는 목표를 7개의 설계 방향으로 압축한다.

What the evidence says

Grounding Context

핵심 재정의: 목표는 세 OS에 같은 패키지를 억지로 넣는 것이 아니라, 같은 개발 능력과 같은 운영 명령을 제공하는 것이다. 설치는 시작일 뿐이며 버전 소유권, 멱등 재실행, GUI/CLI 경계, 인증, 업데이트·제거, 실제 동작 검증까지 같은 계약에 들어가야 한다.

요청된 범위는 WezTerm과 Herdr, 여러 언어·빌드 도구, NvChad 기반 Neovim, Claude Code·OpenCode·Codex, 업무 CLI와 데스크톱 앱, Docker까지 이어진다. 이 도구들은 설치 위치와 수명주기가 다르다. 특히 Herdr는 터미널 에뮬레이터가 아니라 에이전트 상태를 인식하는 멀티플렉서이므로 WezTerm과 별도 컴포넌트여야 한다.

워크스페이스의 기존 학습은 공통 CLI/runtime 코어를 얇은 host adapter 뒤로 수렴시키고, GUI 앱을 Linux/WSL 경계에 억지로 넣지 않으며, 인증을 설치와 분리하고, 지원 상태를 implemented·blocked·verified로 구분하라고 지지한다. 이 프로젝트 자체는 독립 저장소가 source of truth를 소유하고 zWorkspaces에는 submodule로 연결하는 것이 확립된 운영 경계다.

chezmoi

다양한 머신의 dotfile·템플릿·스크립트·비밀 참조를 관리한다. 시스템 패키지 전체의 소유자는 아니다.

mise

개발 도구 버전, 환경변수, task에 강하다. 앱과 시스템 패키지는 범위 밖이며 Windows에는 별도 제약이 있다.

Homebrew Bundle · WinGet Configuration

호스트 네이티브 패키지와 설정을 선언한다. 하나의 공통 manifest가 아니라 OS adapter의 강한 실행 백엔드다.

Dev Container Spec · Herdr

Dev Container는 프로젝트·CI 재현성, Herdr는 에이전트 세션 실행면에 적합하다. 둘 다 전체 데스크톱의 대체물은 아니다.

1

Top pick · One execution path

Environment Intent Graph and Stable Commands

Axis
컴포넌트 그래프와 프로필
Confidence
94%
Complexity
Medium

Description 각 컴포넌트를 단순 설치 스크립트가 아니라 requires, conflicts, owner, supported_hosts, verify를 가진 선언으로 모델링한다. all, backend, flutter, ai-agents는 동일한 그래프를 선택하는 preset이고, 사용자는 백엔드가 바뀌어도 plan, apply, doctor, auth, update, remove라는 작은 명령 계약만 기억한다.

Basis direct: 사용자가 전체 설치와 선택 설치를 동시에 원한다. 두 경로를 따로 만들면 필연적으로 드리프트하므로 하나의 그래프와 여러 선택 표현이 요구를 가장 직접적으로 만족한다.

Rationale 새 도구를 추가할 때 설치 순서, 선택 조합, 지원 OS, 검증 방법이 함께 따라온다. “무엇이 왜 설치되는가”를 실행 전에 설명할 수 있고, 전체 설치도 예외가 되지 않는다.

Downsides manifest schema와 dependency resolution이 초기 Bash 스크립트보다 무겁다. 별도 “컴파일러 IR”까지 만들 필요는 없으며, 먼저 사람이 읽을 수 있는 plan 모델로 제한해야 한다.

2

Parity without pretending

Layered Capability Architecture

Axis
Host/OS 수렴 경계
Confidence
92%
Complexity
Medium

Description “같은 패키지” 대신 java.compile, container.run, terminal.multiplex 같은 능력을 공통 계약으로 정의한다. 구조는 host-native desktop, portable CLI/runtime core, project toolchain의 세 plane으로 나눈다. Windows는 windows-native, wsl-core, windows-host-gui를 명시적으로 구분한다.

Basis external: mise는 dev tool에, Homebrew/WinGet은 host package에, Dev Container는 project/CI 환경에 각각 강한 별도 범위를 가진다. 요청에는 이 세 범위가 모두 포함돼 있다.

Rationale GUI 앱을 Linux 안에 억지로 넣거나 native Windows를 Unix처럼 위장하지 않으면서도, 사용자에게는 같은 기능과 같은 상위 명령을 제공한다. 새 플랫폼은 전체 흐름을 복사하지 않고 해당 capability adapter만 추가한다.

Downsides “동일 환경”의 의미를 패키지 동일성에서 능력 동일성으로 바꾸는 합의가 필요하다. Windows/WSL 경계를 잘못 잡으면 Git, Node, Docker가 양쪽에 중복될 수 있다.

One artifact, one authority

Single-Owner State Router

Axis
패키지·런타임·설정 소유권
Confidence
91%
Complexity
Medium

Description 모든 바이너리와 설정에 정확히 하나의 authoritative manager를 지정한다. 예를 들어 런타임은 mise, dotfile은 chezmoi, GUI·시스템 패키지는 OS adapter, 프로젝트 격리는 Dev Container가 소유한다. 상위 저장소는 직접 모든 것을 설치하기보다 소유권을 라우팅하고 충돌을 탐지한다.

Basis external: 선행 도구의 강점과 범위가 보완적이다. 동일한 Java나 Neovim 설정을 여러 관리자가 건드리면 버전 드리프트, PATH 충돌, 제거 실패가 발생한다.

Rationale “이 파일과 실행 파일을 누가 만들고 업데이트하고 제거하는가?”라는 질문에 한 곳만 답하게 된다. 이 원칙 하나가 장기 유지보수 비용과 장애 원인 탐색 시간을 크게 줄인다.

Downsides OS 패키지 의존성 때문에 완벽한 소유권 분리가 불가능한 경우가 있다. 그때는 primary owner와 external dependency를 구분해야지, 소유권 원칙을 포기해서는 안 된다.

Support claims need evidence

Proof-Carrying Component Contract

Axis
라이프사이클 UX와 검증
Confidence
89%
Complexity
Medium

Description 각 컴포넌트가 detect → plan → install → configure → verify → remove 계약과 최소 기능 시험을 함께 제공한다. “설치됨” 대신 Java 컴파일, Flutter doctor, Neovim headless 실행, Docker 연결 같은 실제 능력을 확인하고 OS별 상태를 implemented, blocked, verified로 기록한다.

Basis direct: 도구 수가 많을수록 누락은 설치 중보다 첫 실제 사용에서 드러난다. 로컬 학습도 환경상 차단된 구현을 검증 성공으로 정규화하지 말라고 요구한다.

Rationale README 체크박스가 아니라 실행 증거가 지원 범위를 정의한다. Herdr도 단순 바이너리 존재가 아니라 agent-session 컴포넌트로, WezTerm은 terminal emulator로 각각 다른 검증 계약을 가진다.

Downsides 컴포넌트 추가 비용이 커진다. 모든 제거를 처음부터 완전 자동화하는 admission rule은 과하므로, 안전한 제거 범위와 수동 handoff를 정직하게 기록하는 수준부터 시작해야 한다.

Built for the second run

Resumable Reconciler and Execution Journal

Axis
라이프사이클 UX와 검증
Confidence
86%
Complexity
High

Description 일회성 순차 스크립트 대신 원하는 상태로 계속 수렴하는 실행기를 둔다. 한 노드가 실패해도 독립 노드는 계속 진행하고, 네트워크·재부팅·관리자 승인 지점에서 journal을 남긴 뒤 다음 실행이 이어받는다. update와 remove도 같은 소유권과 영수증을 사용한다.

Basis reasoned: Java 설치 실패가 Chrome이나 gh 설치까지 막을 이유는 없다. 이미 dependency graph가 있다면 실패 전파를 의존 노드로 제한하고 성공 노드는 재검증만 하는 편이 합리적이다.

Rationale all-in-one 설치의 현실적인 실패를 흡수하고, 6개월 뒤 같은 명령을 실행해도 중복 설치 없이 현재 상태와 원하는 상태의 차이만 교정한다. 최초 설치보다 장기 운영에서 가치가 커진다.

Downsides 가장 비싼 아이디어다. Homebrew·WinGet·mise를 아우르는 원자적 transaction이나 universal lockfile을 약속하면 거짓이 되므로, plan diff·checkpoint·receipt·best-effort recovery로 범위를 제한해야 한다.

Differences are data

Typed Machine Passport and Secret-Free Auth Queue

Axis
시크릿·인증·머신 편차
Confidence
88%
Complexity
Medium

Description work, personal, headless, native-windows, wsl 같은 typed overlay로 머신 차이를 설명한다. environment passport는 resolved version, owner, capability, verification, auth readiness를 한 번에 보여주되 실제 토큰은 담지 않는다. 로그인은 공식 OAuth/CLI 흐름의 별도 queue에서 진행한다.

Basis direct: 요청된 AI·협업 CLI는 대부분 계정 인증이 필요하지만 설치 저장소에 비밀값을 넣을 수 없다. 회사 장비, 개인 장비, WSL, headless Linux의 차이도 피할 수 없다.

Rationale “모든 머신이 동일하다”는 허구를 “차이가 명시되고 검증된다”는 더 강한 재현성으로 바꾼다. 설치 완료와 서비스 사용 가능 상태를 구분하므로 자동화 수준을 과장하지 않는다.

Downsides overlay 수가 늘면 조건 분기가 다시 복잡해질 수 있다. 사유·적용 범위·만료 조건을 요구하고, 실제로 필요한 dimension만 추가해야 한다.

Own the awkward first ten minutes

Fresh-Machine Entry and Honest Host Finish

Axis
Host/OS 수렴 경계
Confidence
80%
Complexity
Medium

Description “repo를 clone한다”는 문장 앞에 숨어 있는 Git·shell 전제를 제거한다. PowerShell과 POSIX shell 같은 OS 기본 진입점이 최소 bootstrap을 받아 repo로 넘긴다. GUI store 로그인, 관리자 승인, 재부팅처럼 자동화할 수 없는 항목은 ordered host-finish queue로 모으고 완료 후 다시 검증한다.

Basis reasoned: 완전히 새 머신에는 Git조차 없을 수 있고, GUI 설치는 host trust model과 사람 승인을 따른다. 이 두 구간을 범위 밖으로 두면 “몇 개 명령” 경험이 가장 중요한 첫 실행에서 깨진다.

Rationale 자동화 불가능한 것을 실패로 숨기지 않고, 사용자의 개입을 짧고 예측 가능한 handoff로 만든다. 설치 경험의 시작과 끝을 모두 제품 표면으로 소유한다.

Downsides 모든 OS의 기본 도구만으로 동작하는 entrypoint를 유지해야 한다. 서로 다른 승인을 한 번의 원자적 ceremony로 묶을 수는 없으므로 queue와 재검증까지만 약속해야 한다.
